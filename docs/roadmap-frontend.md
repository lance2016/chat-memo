# 前端体验与架构 Roadmap

> 状态：Draft<br>
> 最近更新：2026-08-06<br>
> 范围：`frontend/` 的架构、交互、动效、易用性、性能、稳定性与可访问性。

## 1. 目标

这份 Roadmap 不以继续“换一套 UI”为目标，而是让现有“朝花夕拾”界面具备可长期迭代的基础：

1. 页面切换时框架、尺寸和视觉锚点保持稳定。
2. 输入、发送、流式回复、切换会话等关键路径状态可靠，不再依赖偶然的时序。
3. 动效只用于说明状态变化，不制造卡顿、位移或等待感。
4. 桌面端、移动端、键盘和辅助技术用户都能完整使用主要功能。
5. 新功能可以通过组件、设计令牌、统一请求层和自动化测试安全加入。

## 2. 当前基线与主要判断

### 2.1 已经做得较好的部分

- `WorkspaceFrame` 已把侧栏和顶栏提升为持久化框架，路由切换只替换内容区，方向正确。
- 首页和聊天输入已处理 Enter、Shift+Enter 与中文输入法组合态，且发送后能先展示用户问题。
- 删除等高风险操作已有自定义 `ConfirmDialog`，全局搜索和对话框也已有焦点约束的基础。
- 页面已支持明暗主题和 `prefers-reduced-motion`。
- `review/` 已按卡片职责拆分，可作为其他大页面的拆分范式。
- 路由预取、过期请求取消和 `LatestRequest` 已在部分路径应用，说明不需要推翻重做。

### 2.2 核心问题总览

| 优先级 | 问题 | 源码证据/现象 | 影响 |
| --- | --- | --- | --- |
| P0 | 聊天状态耦合且缺少集成测试 | `chat-page.tsx` 约 737 行，同时负责首页、会话、SSE、TTS、CRUD；现有测试集中在 `lib/` | Enter、IME、消息顺序、切会话等竞态容易复发 |
| P0 | 样式层叠已失去边界 | `globals.css` 约 1884 行，存在多轮主题与同名选择器覆盖 | 很小的样式修改也可能让另一个页面位移或尺寸改变 |
| P0 | 请求生命周期不统一 | 只有搜索、聊天和少数页面显式取消请求；通用 `request()` 没有超时、重试策略和错误分级 | 慢请求、切页和断网时容易产生陈旧数据或无限等待 |
| P1 | 移动端导航仍需完整验证 | `<=720px` 已增加五项底部导航，但软键盘、安全区域和 200% 缩放尚无自动化验证 | 小屏和辅助技术场景仍可能回归 |
| P1 | 反馈与恢复能力不足 | Loading、Empty、Error 分散实现；缺少全局 toast 和 Error Boundary | 用户不知道是否成功，也缺少“重试/撤销/恢复”路径 |
| P1 | 可访问性和键盘路径未被测试 | 有部分焦点管理，但没有 a11y、组件或 E2E 测试 | 对话框、菜单、流式消息和移动导航容易出现回归 |
| P2 | 动效没有统一语义 | 同时存在 `page-enter`、`soft-in`、`surface-in` 等历史规则，后部覆盖层又禁用了部分动画 | 页面有时“跳”、有时“淡入”，体感不一致 |
| P2 | 首次加载和长列表仍有优化空间 | Shiki、diff 等重依赖进入前端依赖；会话、记忆和变更列表缺少虚拟化 | 首屏解析、低性能设备和长数据集体验下降 |
| P2 | Review 数据获取成本偏高 | 切换日期会并行请求多个接口，并拉取 active/archived 会话后在前端筛选 | 延迟、流量和后端压力随数据量增长 |
| P3 | 个性化信息仍有硬编码 | 侧栏与首页存在 `Lance` 等固定文案 | 多用户/部署配置与 UI 不一致 |

### 2.3 架构判断

当前问题不是 Next.js 路由本身，而是“持久框架之下的页面状态、CSS 和数据请求仍各自为政”。因此应保留 App Router 和 `WorkspaceFrame`，渐进拆分页面；不建议再次做一次性全量重写。

前端目前也处于 Tailwind 已安装、界面主要依赖手写 CSS 的双轨状态。应明确一个方向：短期保留 CSS Modules/分层 CSS 并使用设计令牌，或者完整采用 Tailwind；不要长期让两套体系同时承担同一职责。本 Roadmap 默认选择前者，因为迁移风险更低。

## 3. 实施原则

1. **框架常驻，内容切换**：侧栏、顶栏、内容区外边距和主要操作位置不得随路由重建或改变尺寸。
2. **状态先于动画**：先保证用户输入、服务端权威消息和流式草稿的状态转换正确，再增加过渡效果。
3. **乐观展示，可明确恢复**：发送、重命名、归档等操作要即时反馈；失败时可重试或回滚。
4. **动效不参与布局**：避免对宽高、边距、整体页面做动画，优先使用 opacity 和小幅 transform。
5. **默认可访问**：键盘、触屏、中文输入法、减少动态效果等不是补丁，而是验收条件。
6. **用测试固定已修复问题**：每个历史严重问题都应转化为回归用例。
7. **先测量再优化**：性能、包体和动画流畅度以生产构建及真实设备指标判断，不以开发模式体感代替。

## 4. 分阶段 Roadmap

### Phase 0：建立基线（P0，约 1～2 天）

#### FE-001 建立可重复的体验与性能基线

- 问题：当前“卡顿”“变大”“没对齐”主要依赖人工感受，修复后难以证明未回归。
- 动作：
  - 固定桌面 1440×900、窄桌面 900×900、移动端 390×844 三组视口。
  - 记录 `/`、`/memories`、`/review`、`/timeline`、`/settings` 的首屏与互相切换截图。
  - 记录生产构建各路由 First Load JS、Web Vitals、切换路由期间的 CLS 和长任务。
  - 建立关键路径手工检查表，后续逐步转为 Playwright。
- 验收标准：
  - 基线结果可在同一机器上一条命令重复生成。
  - 五个路由的侧栏宽度、顶栏高度、内容起始坐标可自动比较。
  - 路由切换期间框架区域 CLS 接近 0，内容区 CLS ≤ 0.05。

#### FE-002 定义页面骨架契约

- 问题：不同页面仍可自行定义 shell 高度、滚动容器和内容边距。
- 动作：定义唯一的 `WorkspaceFrame -> PageHeader -> PageContent` 布局契约，明确桌面、折叠侧栏、移动端三个断点的固定尺寸和滚动归属。
- 验收标准：
  - 侧栏和桌面顶栏只在根 layout 挂载一次。
  - 路由切换不改变导航、品牌、主操作按钮的尺寸和坐标。
  - 每个页面只能有一个主滚动容器，不出现 body 与内容区双滚动。

### Phase 1：稳定性与可维护性（P0，优先实施）

#### FE-101 拆分聊天状态机

- 问题：聊天页同时处理首页、会话加载、乐观消息、SSE、TTS、标题、归档与删除，状态更新互相影响。
- 动作：
  - 提取 `useConversationSession`：会话选择、创建、历史加载和请求世代号。
  - 提取 `useStreamingChat`：发送、取消、SSE 草稿、最终消息和错误恢复。
  - 提取 `useSpeechPlayback`：队列、播放状态、停止和资源释放。
  - 拆出 `HomeWelcome`、`ConversationView`、`MessageList`、`ChatComposer`、`ConversationActions`。
  - 为状态定义明确阶段：`idle -> submitting -> streaming -> completed/failed/cancelled`。
  - 历史请求只能提交给发起它的会话；新请求开始后，旧请求不得清空 `pendingUser` 或覆盖消息。
- 验收标准：
  - 用户按发送后 100ms 内显示自己的问题，不能等回答完成后才出现。
  - 新会话的旧历史请求返回时，不得清掉乐观消息。
  - SSE 首 token、最终消息对账时不闪烁、不重复、不倒序。
  - 切换会话或离开页面会中止当前请求并释放 TTS/audio 资源。
  - 首页输入框和会话输入框复用同一个键盘/IME 行为组件。
- 依赖：FE-001。

#### FE-102 为历史问题补回归测试

- 问题：现有 Vitest 用例主要覆盖 `api`、`tree`、`turns`、`latest-request`，没有组件和路由级保护。
- 动作：先增加 React Testing Library 组件测试，再补最小 Playwright E2E 集合。
- 必测场景：
  1. 首页 Enter 发送，Shift+Enter 换行。
  2. 中文输入法 `compositionstart` 至 `compositionend` 期间 Enter 只选词、不发送。
  3. 首页发送后进入会话，问题立即可见。
  4. SSE 草稿切换为服务端最终消息，无重复和闪烁。
  5. 连续切换两个会话，后返回的旧请求不能覆盖当前会话。
  6. 删除、归档、截断消息必须经过自定义确认并正确更新列表。
  7. 从五个主路由互相切换时，持久框架不卸载、不改变几何尺寸。
- 验收标准：上述用例在 CI 无头浏览器稳定通过；每个已发现的竞态至少对应一个失败过、修复后通过的测试。

#### FE-103 统一请求生命周期

- 问题：`lib/api.ts` 统一了 URL 和错误文本，但没有默认超时、重试、去重、缓存及一致的 AbortSignal 入口。
- 动作：
  - 所有查询支持外部 `AbortSignal`；页面卸载、筛选条件变化和新请求开始时取消旧请求。
  - 配置查询超时和流式请求的空闲超时；区分取消、超时、离线、4xx、5xx。
  - GET 请求允许有限重试和抖动退避；变更请求默认不自动重试，除非具备幂等条件。
  - 给会话列表、运行时设置、健康检查定义缓存和失效策略。
  - 可评估 TanStack Query/SWR，但引入前先写小型 ADR；不为“统一”而一次性迁移所有调用。
- 验收标准：
  - 页面上不存在无限 loading。
  - 快速切日期、搜索和会话不会展示陈旧响应。
  - 断网、超时和服务端错误有不同提示，且在可恢复场景提供“重试”。

#### FE-104 增加全局错误与操作反馈层

- 问题：错误提示散落在页面，成功操作通常没有统一反馈；组件渲染异常可能让整个内容区空白。
- 动作：
  - 在 route segment 增加 `error.tsx` 和 `loading.tsx`，在应用层增加 Error Boundary。
  - 建立统一 Toast/Notice 服务，支持 success、info、warning、error 和操作按钮。
  - 删除优先采用“确认 + 明确结果”；适合软删除的对象再增加撤销，不能恢复时不要伪造撤销。
  - 用应用内对话框处理未保存内容的站内导航；浏览器 `beforeunload` 仅保留浏览器规定的系统提示。
- 验收标准：
  - 未捕获渲染异常能展示恢复入口，不导致持久框架消失。
  - 保存、归档、删除、备份、设置更新均有一致反馈。
  - `navigation-guard.ts` 的站内路径不再调用 `window.confirm`。

#### FE-105 清理 CSS 架构

- 问题：单个 `globals.css` 承载历史主题、组件、响应式和修复覆盖，同一选择器多次重定义。
- 动作：
  - 先建立视觉快照，再按 `tokens / reset / frame / primitives / pages / utilities` 分层。
  - 将颜色、字号、间距、圆角、阴影、层级、断点和动效时长提取为设计令牌。
  - 页面私有样式迁入 CSS Modules；全局文件仅保留令牌、基础样式和真正跨页的 primitives。
  - 删除无引用选择器、重复主题块和依赖源码顺序生效的末尾补丁。
  - 在完成迁移前冻结新的全局页面选择器。
- 验收标准：
  - `globals.css` 不再包含具体页面的大段实现，且不存在重复定义后靠更后规则纠正的核心选择器。
  - 五个路由的视觉快照无非预期差异。
  - 修改按钮或页面容器样式时，不需要在文件尾新增覆盖规则。
- 依赖：FE-001、FE-002。

### Phase 2：易用性与可访问性（P1）

#### FE-201 补齐移动端信息架构（导航 MVP 已实现）

- 现状：移动端底部导航已包含首页、记忆库、每日回顾、时间线和设置。
- 后续动作：补齐主输入区的安全区域和软键盘适配，并增加断点、缩放与键盘测试。
- 验收标准：
  - 390px 宽度下可在两次点击内到达任一主页面。
  - 所有点击目标至少 44×44 CSS px。
  - 打开软键盘后，输入框、发送按钮和最新消息仍可见且可操作。

#### FE-202 改善对话核心体验

- 动作：
  - 草稿按会话保存；切走再回来不丢失，发送成功后才清除对应草稿。
  - 流式时提供停止生成；失败消息就地提供重试，不要求重新输入。
  - 自动滚动只在用户位于底部时执行；用户上翻后显示“回到最新消息”。
  - 消息操作统一为复制、重新生成、朗读/停止、必要时删除或截断。
  - 空会话、加载历史、模型思考、首 token 等待、流式生成使用不同但克制的状态文案。
- 验收标准：
  - 会话切换和刷新后草稿按约定恢复。
  - 用户阅读历史消息时，不被新 token 强制拉回底部。
  - 失败后可一键重试，且不会生成重复用户消息。

#### FE-203 统一 Loading / Empty / Error / Success

- 动作：为列表、详情、卡片、搜索、流式聊天定义统一状态组件；首屏用与最终布局同尺寸的 skeleton，局部刷新保留旧内容并显示轻量进度。
- 验收标准：
  - 无空白页和仅显示“加载中”的布局跳变。
  - 空状态说明“为什么为空”和“下一步做什么”。
  - 后台刷新不清空已有内容。

#### FE-204 提升设置页可发现性

- 动作：增加设置搜索、类别锚点、修改状态提示和“恢复默认值”；知识库状态应展示路径、索引/文件数量、最近更新时间、健康状态与刷新入口。
- 验收标准：
  - 输入中文关键字能定位模型、知识库、TTS、调试等设置。
  - 有未保存变更时离开会明确提示，保存后提示消失。
  - 前端只展示后端实际支持且在 API 文档中定义的配置。

#### FE-205 消除硬编码身份与环境信息

- 动作：侧栏头像、称呼和首页欢迎语从运行时设置读取 `OWNER_NAME`，缺失时使用中性文案；API 地址、模型和知识库状态统一来自配置/健康接口。
- 验收标准：修改 `.env` 并重启后，界面不再残留 `Lance` 等固定值；配置缺失时有合理 fallback。

#### FE-206 完整键盘与辅助技术支持

- 动作：
  - 公共 Dialog primitive 统一焦点锁定、初始焦点、Esc 关闭、关闭后焦点归还。
  - 菜单、Tabs、搜索结果使用正确角色和方向键行为。
  - 为流式回复使用克制的 `aria-live` 策略，避免每个 token 重复播报。
  - 明确 focus-visible 样式、文本对比度和错误字段关联。
  - active 导航保留为可点击链接，允许回到根路径或清除 query，而不是不可操作的 `span`。
- 验收标准：
  - 不使用鼠标可完成发送消息、搜索、切页、编辑记忆和设置保存。
  - axe 核心页面无 critical/serious 问题。
  - 200% 缩放下无关键内容裁切，明暗主题均满足 WCAG AA 的主要文本对比度。

### Phase 3：动效与视觉一致性（P2）

#### FE-301 建立 Motion Tokens

建议只保留三档时长：

| Token | 建议值 | 使用场景 |
| --- | ---: | --- |
| `--motion-fast` | 100～120ms | hover、pressed、图标状态 |
| `--motion-normal` | 160～180ms | tooltip、菜单、toast、小范围展开 |
| `--motion-slow` | 200～240ms | dialog、抽屉、主要内容首次呈现 |

缓动只保留 standard、enter、exit 三种。所有动效必须复用令牌，不允许组件自行增加 300ms 以上的装饰性等待。

#### FE-302 定义动效语义

| 场景 | 建议 | 禁止 |
| --- | --- | --- |
| 主路由切换 | 框架静止；内容可做 120～160ms 轻微淡入 | 整页缩放、侧栏重入、容器宽高动画 |
| 首次数据加载 | 同尺寸 skeleton 交叉淡化为内容 | spinner 后突然换成不同高度内容 |
| 消息发送 | 用户气泡即时出现；发送态仅改变局部状态 | 等服务端响应后再显示问题 |
| 首 token | 思考状态平滑替换为文本 | 重新挂载整个消息列表 |
| 展开/折叠 | 小内容可用 opacity/transform；大内容即时布局 | 对未知高度长期运行 `height` 动画 |
| Dialog/抽屉 | 遮罩 120ms，内容 180～220ms，退出更快 | 背景和页面框架同时缩放 |
| Toast | 轻微上移淡入，自动消失前保留足够阅读时间 | 无法暂停或来不及操作 |
| 首页 Logo | 可保留低频、低振幅的品牌呼吸/轨道效果 | 高频旋转、影响点击区域或触发布局 |

#### FE-303 Reduced Motion 与性能约束

- `prefers-reduced-motion: reduce` 下关闭轨道、位移、缩放和光效，仅保留必要的即时状态变化。
- 动画只使用 compositor 友好的 opacity/transform，并避免在长列表每一项同时进场。
- 动效不得延迟请求、输入响应或导航；JS 动画必须可取消并在卸载时清理。
- 验收标准：中低端移动设备路由和 Dialog 动画无明显掉帧；减少动态效果模式下所有功能和状态含义仍完整。

### Phase 4：性能与规模化（P2）

#### FE-401 拆分重依赖和非首屏功能

- 动作：对 Shiki 代码高亮、diff、调试详情、TTS 控制和大型设置分区做动态加载；普通文本消息不加载高亮器。
- 验收标准：以 Phase 0 基线为准，首页初始 JS 至少降低 15%，且动态模块加载时不阻塞输入与消息展示。

#### FE-402 优化数据获取

- 动作：
  - Review 使用后端日期过滤或聚合接口，避免每次拉取 active/archived 各 200 条会话再前端筛选。
  - 同一路由内的相同查询去重；导航预取与页面请求复用结果。
  - 低频稳定数据采用合理缓存，高频对话数据通过精确失效更新。
- 验收标准：切换回顾日期的请求数和传输数据显著下降；重复进入页面不重复拉取未失效数据。

#### FE-403 长列表与 Markdown 性能

- 动作：会话数、记忆节点或版本记录达到阈值后启用虚拟化/分页；流式 Markdown 降低全量重解析频率；消息组件使用稳定 key 和边界明确的 memoization。
- 验收标准：1000 条会话、1000 个记忆节点、200 条长消息的基准数据下，滚动保持可用，单次流式更新不触发整页重渲染。

#### FE-404 建立性能预算

建议初始预算（生产环境、经团队基线校准后固化）：

- LCP：桌面 p75 ≤ 2.5s，移动 p75 ≤ 4.0s。
- CLS：页面加载与路由切换均 ≤ 0.05。
- INP：p75 ≤ 200ms。
- 主路由缓存命中后的点击到可交互反馈 ≤ 200ms。
- 单次前端长任务不超过 50ms；新增依赖导致主包增长超过 15kB gzip 时必须说明理由。

### Phase 5：质量体系与产品增强（P3，持续）

#### FE-501 自动化质量门禁

- Pull Request 必须通过 lint、typecheck、unit/component tests 和 production build。
- 核心路由增加 Playwright smoke test、axe 检查和视觉回归。
- API 类型尽可能从 OpenAPI 生成或在 CI 做契约差异检查，`docs/frontend-api.md` 与后端变更同步。
- 关键前端异常记录路由、操作、请求 ID 和错误类别，但不得记录用户消息正文、API Key 或私密记忆。

#### FE-502 提升发现与效率

- 将全局搜索扩展为 Command Palette：新建记录、跳转页面、打开最近会话、进入设置。
- 记忆库增加筛选、排序、最近修改和清晰的版本恢复入口。
- 新用户首次进入时展示最小化 onboarding：数据保存位置、模型配置、知识库状态、如何开始第一段对话。
- 所有增强先通过真实任务验证，不为了“功能丰富”增加常驻视觉噪声。

## 5. 推荐实施顺序

```text
体验/性能基线（FE-001）
  ├─ 页面骨架契约（FE-002）── CSS 清理（FE-105）── 动效规范（FE-301~303）
  └─ 聊天状态拆分（FE-101）── 回归测试（FE-102）
                         └─ 请求层与反馈（FE-103~104）
                                      └─ 易用性与 a11y（FE-201~206）
                                                   └─ 性能与质量门禁（FE-401~501）
```

最先落地的三个迭代建议：

1. **稳定聊天**：FE-101、FE-102、FE-103，直接降低当前最严重的状态回归风险。
2. **固定框架**：FE-001、FE-002、FE-105，解决切页尺寸变化和样式互相污染。
3. **补齐使用闭环**：FE-104、FE-201、FE-202、FE-206，再进入动效和性能精修。

## 6. 每次发布的回归清单

### 聊天

- [ ] 首页和会话页 Enter 发送、Shift+Enter 换行。
- [ ] 中文输入法选词 Enter 不发送。
- [ ] 发送后先显示问题，再显示思考/回复。
- [ ] SSE 完成后无重复、闪烁、倒序或消息消失。
- [ ] 切换会话不会串消息，草稿和滚动位置符合预期。
- [ ] 停止生成、失败重试、TTS 停止可用。

### 导航与布局

- [ ] 五个主页面切换时侧栏、品牌、主按钮、顶栏尺寸不变。
- [ ] active 状态准确，带 query 的首页会话链接可正常切换。
- [ ] 首次进入未预热路由时有稳定 skeleton，无白屏和双滚动。
- [ ] 390px、720px、980px 断点附近无导航丢失或内容溢出。

## 7. Definition of Done

单个前端改进只有同时满足以下条件才算完成：

- 行为有明确验收标准，历史 bug 有自动化回归用例。
- Loading、Empty、Error、Success 和取消路径均被处理。
- 桌面、移动、键盘、中文输入法、明暗主题和 reduced-motion 已检查。
- 没有新增无约束的全局 CSS、硬编码环境信息或无法取消的异步请求。
- 生产构建、lint、typecheck、测试通过，且性能预算没有无说明退化。
- 文档和 API 契约随行为变化同步更新。

## 8. 非目标与风险控制

- 不进行第二次一次性视觉重写；所有改动基于现有品牌语言渐进完成。
- 不用动画掩盖慢请求，也不为“顺滑”延迟用户输入和路由响应。
- 不在缺少基线时盲目引入大型状态管理、动画或组件库。
- 不为了减少文件行数机械拆分；拆分边界应对应状态所有权、加载边界或可复用交互。
- 涉及 Review 聚合接口、幂等发送、知识库诊断等后端能力时，先更新 `docs/frontend-api.md` 并以契约为依赖，不在前端猜测字段。
