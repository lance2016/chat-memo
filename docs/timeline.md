# 时间线模块

> 状态：第二版已实现（主动通知）
>
> 首次实现：2026-08-07
>
> 范围：对话提取、结构化存储、API、今天/最近/月历视图、人工校正、到点推送到手机。

## 产品定位

时间线把对话里散落的未来事项变成可操作的结构化记录，包括待办、会议、提醒、生日、
旅行、截止日期和重要时间节点。它不替代长期记忆，也不替代每日回顾中的关注事项：

- `Memory` 保存长期背景事实。
- `OpenLoop` 保存没有明确日期、之后可能仍需关注的问题、决定或后续动作。
- `TimelineItem` 保存有明确日期或时间、适合按日程查看的事项。

## 第一版能力

- 模型工具：`timeline_list`、`timeline_create`、`timeline_update`。
- 明确安排直接记为 `confirmed`；“可能、也许、暂定”记为 `pending`。
- 创建前可查询近期事项，改期、完成和取消应更新原记录，避免重复。
- `/timeline` 提供“今天”“最近 30 天”“月视图”。
- 支持手动创建、确认模型提取结果、完成、重新打开和删除。
- 模型创建的事项保留来源会话，可从时间线跳回原对话。
- 移动端增加五项底部主导航，时间线不再只能从桌面侧栏进入。

## 数据模型

`timeline_items` 的关键字段：

| 字段 | 说明 |
|---|---|
| `kind` | `todo/event/reminder/birthday/travel/deadline/note` |
| `status` | `pending/confirmed/completed/cancelled` |
| `starts_at`, `ends_at` | 带时区的时间；开始时间必填 |
| `all_day`, `timezone` | 全天事项与原始 IANA 时区 |
| `location`, `recurrence` | 地点；第一版支持 `none/yearly` |
| `actor` | `chat` 或 `manual` |
| `source_conversation_id` | 模型提取时的来源会话 |

来源 ID 不设外键：删除原会话不会连带删除用户已经确认的日程。

## 提取边界

模型只应记录未来且具有时间依据的事项。过去事件、泛泛愿望、没有日期的想法不进入时间线；
后者如果之后仍可能需要关注，可以由每日整理进入 OpenLoop。两个区域互斥：一旦有明确日期、
时间、提醒或截止期限，就应进入时间线，不再重复进入 OpenLoop。相对日期以每轮注入的当前时间和 `TZ`
为准，工具时间必须使用包含 UTC offset 的 ISO 8601。

## API

```http
GET    /api/timeline?from=<ISO>&to=<ISO>&status=pending,confirmed
POST   /api/timeline
PATCH  /api/timeline/{id}
DELETE /api/timeline/{id}
```

创建示例：

```json
{
  "title": "和产品团队开会",
  "kind": "event",
  "status": "confirmed",
  "starts_at": "2026-08-10T15:00:00+08:00",
  "ends_at": "2026-08-10T16:00:00+08:00",
  "timezone": "Asia/Shanghai",
  "location": "线上"
}
```

## 第二版：主动通知

> 实现时间：2026-08-07

到点了会把事项推到手机上。这一版同时修掉了两个让事项**静默丢失**的缺陷 ——
不修的话通知漏一次，那件事就再也不会出现在任何视图里。

### 修掉的两个缺陷

**逾期静默消失。** 「今天」视图原来严格按 `[今天00:00, 明天00:00)` 查，昨天没勾掉的
事从今天和最近视图里一起消失，只有翻月历才找得回来。现在 `TimelineStore.list` 有
`include_overdue`，今天和最近视图默认带上，逾期项单独成组排在最前面。

**`recurrence=yearly` 从来没生效过。** 字段在 model、API、工具 schema 和前端徽标里
都有，但查询是纯 `starts_at` 范围过滤 —— 2026 年记的生日在 2027 年的月历里什么都不
显示，这个字段唯一的作用是在卡片上印「每年重复」四个字。现在 `list` 会把每年重复的
事项投影到查询区间（`project_yearly`）。投影返回的是**未加入 session 的副本**：
直接改原对象会在 flush 时把生日永久挪到当年。2 月 29 日在非闰年落到 28 日。

### 提醒是怎么触发的

数据层在 `timeline_items` 上加了四列：

| 字段 | 说明 |
|---|---|
| `notify` | 这一条要不要提醒。关掉但保留事项本身 |
| `lead_minutes` | 提前量。NULL = 按 kind 取默认 |
| `remind_at` | 派生自 `starts_at - lead`，**存下来**才能让 ticker 一条带索引的 SQL 扫完 |
| `snoozed_until` | 通知里点了「稍后」 |

默认提前量按类型内置（`app/notify/schedule.py`）：会议 15 分钟，出行和生日提前一天，
截止日期提前三天，`note` 不提醒。全天事项的 `starts_at` 是当地 00:00，会先换算到当天的
`notify_all_day_hour` 再减提前量 —— 否则「明天生日」会在今天凌晨零点响。

调度是**补跑式**的：ticker 每分钟查「该发而没发的」，不是「这一秒到点的」。
`app/jobs/scheduler.py` 里已经记过这个教训 —— 进程一重启计时器就从头开始，笔记本凌晨
多半在睡眠，定时触发在这台机器上必然漏。代价是要挡住补跑风暴，两道闸：开始时间已经
过去 `notify_catchup_hours` 的事项不再单独响（交给每日简报兜底），单次 tick 最多 5 条。

幂等和重试都在 `notifications` 表上。`dedupe_key` 唯一约束挡住重复发送；但通道抽风
一分钟不等于「这条提醒没了」，所以没送成的记录留着可重试，到 3 次才放弃。改期和 snooze
都会换 key —— 换了就是一条新提醒，本来就该再响一次。

### 通道

`app/notify/channels.py` 里一个通道就是「把 `PushMessage` 送到某处」，失败抛
`ChannelError`。调度侧不知道有几个通道。第一个实现是 **Bark**（iOS 自建推送，服务端
POST 一个 URL 就完事，手机不需要开着浏览器）。Web Push 会是第二个：它要 VAPID 密钥和
订阅表，但对外仍然是同一个接口，在设置里 `notify_channels` 加一个名字即可。

通知里的「点开跳转」需要 `notify_public_base_url` 填手机访问得到的局域网地址 ——
手机点不开 localhost。留空则不带链接。

### 文案由模型写

日历给你「15:00 产品评审」。这里给的是「十五分钟后和产品团队开会，你上周说想提重复检测
那件事」。正文走标题那条便宜链路（`app/llm/title.py`），输入是事项字段加来源会话最近
一次的复盘。**拿不到模型或返回空一律退回模板** —— 提醒必须发出去，文案好不好是第二位的。

### 每日简报

每天 `notify_briefing_hour` 一条，含今天的事项、逾期未完成、挂了两周以上的待确认。
三段都空就不推 ——「今天没有安排」每天来一条纯属噪音。错过整个窗口（默认 6 小时）就跳过
这一天，而不是晚上十点推一条「今天有三件事」。

## 后续阶段

1. Web Push 通道，让不装 Bark 也能收到。
2. 通知点开后落进一轮**预置了上下文的新对话**，而不只是跳回来源会话 ——
   「提醒即对话的开端」这一步目前只做了一半。
3. 待确认事项的批量处理与重复检测强化；创建时的冲突提醒。
4. 把时间线接进全局搜索（`app/search.py` 目前只覆盖对话和记忆）。
5. 每轮把「今天/明天的事项」注入 runtime_context，让模型开口就知道你今天有什么，
   而不必先调 `timeline_list`。
6. ICS 导入导出和外部日历同步。

外部日历写入仍然不做，避免在提取准确性尚未验证前扩大副作用。
