# 评测数据集

这个目录装的是**记忆整理评测的样本**。整套方案在 [docs/evaluation.md](../docs/evaluation.md)，
这里只讲怎么用、怎么加、怎么标不错。

## 为什么样本在仓库里有特殊地位

评测代码是脚手架，数据集才是资产。

重放脚本、judge prompt、报告格式都可以推倒重写，一个下午就能补回来。
样本不行 —— 一条样本要挑一天真实对话、冻结当时的记忆快照、逐条标出「这次整理
应该产生什么变化」，几十分钟起步，而且**标注的判断本身是不可复现的**：
半年后再看同一天，你已经不记得当时为什么觉得那句话值得记了。

所以这里的约定是围绕「样本要活得比代码久」定的：

- 存**朴素 JSON**，不用 pickle、不进数据库。可以 diff、可以手改、可以 code review
- 契约写在 [`app/eval/dataset.py`](../app/eval/dataset.py)，字段少而稳。加字段前先想想
  能不能塞进 `note`
- 每条样本自带 `note`，写清楚**这条测什么、为什么挑它** —— 唯一防止样本变成
  无人敢动的黑盒的东西
- [`tests/test_eval_dataset.py`](../tests/test_eval_dataset.py) 每次 `pytest` 都会把
  全部样本读一遍、跑一遍 `validate()`。JSON 没有编译期，这个测试就是编译期

## 目录结构

```
evals/
├── README.md      ← 你在这
└── cases/         ← 一个文件一条样本，NN-简短英文描述.json
```

一条样本 = 「某天的对话 + 整理前的完整记忆快照 + 期望产生什么变化」。

现有的六条是**编造的示例**，覆盖六种不同的情形：

| 文件 | 测什么 |
|---|---|
| `01-new-preference.json` | 新事实写入。从零开始的记忆库，稳定事实藏在闲聊里 |
| `02-conflict-correction.json` | 冲突修正。旧记录该被改掉而不是和新说法并存 |
| `03-no-op-technical-day.json` | 反例。一整天纯技术问答，正确行为是什么都不写 |
| `04-signal-among-noise.json` | 信噪比。该记的和大量一次性技术细节混在一起 |
| `05-cross-session-dedup.json` | 多会话去重。同一件事被三个会话各提一角，该合并成一条 |
| `06-index-gap.json` | 索引维护。快照里有个「文件存在但索引没条目」的缺口 |

## 加一条样本

### 从真实数据导出（默认做法）

```bash
uv run python -m app.eval export --day 2026-04-15
```

导出那天的 conversation summaries 和当时的记忆快照，生成一个 `expect` 还空着的
JSON 骨架。**导出只给输入，标注永远是手工的** —— 让模型标自己的期望输出，
评的就成了「模型和自己一致吗」。

然后：

1. 把文件挪进 `cases/`，重命名成 `NN-简短英文描述.json`（`id` 字段要和文件名主干一致，
   测试会查）
2. 按下面的 checklist 填 `expect`
3. 写 `note`
4. `uv run pytest tests/test_eval_dataset.py -q`

### 手工写

需要构造现实里不常发生、但必须覆盖的情形时（比如故意留索引缺口）就手写。
照着 `cases/` 里最接近的一条改，比从空文件开始快得多。字段含义看
`app/eval/dataset.py` 的 docstring。

### 选哪天

- 优先挑**混杂**的一天。全是技术问答或全是生活闲聊的日子区分度低，
  好模型和坏模型都能拿一样的分
- 挑几天**什么都不该记**的。见下面第 2 条原则
- 别只挑「整理得漂亮」的那几天。数据集会变成模型的名人堂，测不出退化

数据集从 20 条起步就够。到 50 条以上再考虑分开发集/测试集，现在分只是仪式感。

## 标注 checklist

三条原则来自 [docs/evaluation.md 第四节](../docs/evaluation.md)，这里写成能逐项对着做的形式。

### 1. 标事实点，不标文本

同一件事有一百种写法都对，逐字比对没有意义。

- [ ] 每条 `facts` 是**一句话、一个事实点**。写成一段就拆开
- [ ] 用陈述句写「应该被记住的事」，不要写「应该在 profile/basics.md 里加一行说……」——
      落在哪个文件是模型的自由
- [ ] `forbidden` 也要具体到能查。写「SSE 断流的排查过程和 proxy_buffering 配置」，
      不要写「技术细节」

常见错误：

- **把摘要抄进 facts**。抄一段进去，判分时就只能整体打分，二值判定退化成主观分
- **标了模型「大概率会写」的东西**，而不是「应该写」的东西。标注是标准，不是预测
- **忘了 forbidden**。只标该记什么，评测就只会奖励写得多的模型

### 2. 必须有反例

只测正例的评测会奖励一个疯狂写记忆的模型。

- [ ] 数据集里有几天是 `no_op: true`
- [ ] `no_op` 的样本里 `facts` 和 `corrections` **必须为空**（`validate()` 会查）
- [ ] `no_op` 样本仍然要写 `forbidden` —— 说清楚模型最可能错记成什么，
      光一个布尔值判不出它错在哪
- [ ] 正例样本里也带上 `forbidden`：同一天里「该记的」和「不该记的」挨在一起，
      比整天都不该记更难

### 3. 快照要冻结

「和旧记录冲突时改掉旧的」只有在起始状态确定时才可复现。

- [ ] `memory_before` 含 `/memories/MEMORY.md`。没有索引，模型的起始视野就是空的
- [ ] 索引每行是 `- [标题](相对路径) — 主题范围`，破折号后不超过 25 字
      （见 [`app/memory/prompt.py`](../app/memory/prompt.py)）。写错格式，样本本身就是脏输入
- [ ] 索引条目和快照里的文件一一对应 —— **除非你是故意留缺口**，
      那种情况要在 `note` 里写明是刻意的
- [ ] `corrections[].stale` 是从快照里**原样复制**的片段，不是凭印象写的同义句。
      判分靠子串匹配，差一个字就永远判成「已改掉」，于是新旧并存这种最糟的失败被静默放过
      （`validate()` 会查这一条）
- [ ] 改了 `memory_before` 就回头检查所有 `stale` 还对不对

### 4. 写 `note`

- [ ] 说清楚**这条测什么**、**为什么挑这天**、**最想抓的失败长什么样**
- [ ] 写给半年后的自己，那时你已经完全不记得这天发生过什么了
- [ ] 边界用例尤其要写。比如「显示器参数虽然关于一个真实的人，但它是一次性购物需求」——
      这种判断不写下来，下次 review 的人会以为是标漏了

## ⚠️ 真实样本包含个人信息

`cases/` 里现在这六条是**编的** —— 内容是为了覆盖六种情形而设计的，不是任何人的真实对话。
所以它们进 git 没有问题。

**从真实数据导出的样本不是这样。** 一条样本冻结的是某一天的完整对话和完整记忆快照，
里面必然有住址、人名、健康状况、工作内容、私人关系 —— 记忆整理这个任务的评测对象
本来就是「关于这个人的事实」，脱敏等于把被测的东西删掉。

加真实样本之前先决定它们进不进 git：

- **不进**：在 `.gitignore` 里排掉真实样本（例如另开 `evals/private/`），
  只保留示例样本。仓库随时可以公开，代价是数据集不跟着代码走，换机器要手动同步
- **进**：数据集和代码一起版本化，这是它作为资产最舒服的形态。
  但从此这个仓库**必须当私有仓库对待** —— 开源计划、贴给别人看的 diff、
  CI 日志都要重新审一遍

现在还没有真实样本，所以这个决定还没做。加第一条之前先做它，
比事后从 git 历史里清理容易得多。
